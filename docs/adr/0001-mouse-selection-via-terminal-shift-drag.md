# Rely on terminal-native Shift-drag for text selection, not an in-app selection engine

Adding mouse support means enabling `EnableMouseCapture`, which also swallows the terminal's own drag-to-select — the two pull in opposite directions since the user asked for both click-to-focus and text selection. We chose to keep `EnableMouseCapture` on for click/scroll handling and lean on the xterm-family convention that holding Shift during a drag bypasses app-level mouse reporting and falls back to terminal-native selection, rather than building an in-app drag-selection engine (tracking drags across wrapped rows, rendering a highlight, extracting selected text to the OSC 52 clipboard).

The alternative was reimplementing selection ourselves on top of the existing `yy`/`yb` copy keys — more surface, more code, and duplicate of what terminals already do well. The cost is discoverability: users must learn to hold Shift to select text, which we call out in the README. Same convention is reused for OSC 8 hyperlink passthrough (see ADR 0002's sibling decision in the same change) and is documented as "mouse" toggle fallback: turning the `mouse` config option off restores full keyboard-only behavior with unmodified native selection.
